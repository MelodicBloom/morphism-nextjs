## Repository-specific records

### D27 — Morphism UI Playground: an instrument for learning tactile behavior

**Use when:** When working on morphism-nextjs, clay/glass controls, synthesizer keys, orbital typewriter, spring experiments, or multisensory demos.

[Recovered intent] This playground combines a clay synthesizer, orbital typewriter, physics-state gallery, live damping controls, particles, and a lagging cursor glow. Its purpose is experiential exploration of tactile interfaces, not merely an extra copy of Mochi.

[Stack and functions] The README names Next/React/TypeScript, Tailwind, Framer Motion, GSAP, Web Audio, speech, vibration, and hooks for audio, haptics, physics, and particle bursts. These are documented components/functions, not proof that every path is robust.

[Repair resolution — proposed] Keep an experiment surface separate from the reusable library. Trace each behavior back to an owned token/preset; do not let a copied ClayButton become another undocumented authority. Ensure one animation runtime owns each property and expose audio/speech/haptics as optional capabilities with cancellation.

[Reimagined horizon] A learnable instrument: press, hear, see, adjust a parameter, compare trajectories, and understand how material character changes. Publish discoveries back as tested patterns rather than importing all experiments into product controls.

[Carry-forward test] One keyboard and typewriter can be operated without pointer input or sound; changing a spring parameter yields a measurable, bounded change; reset/cancel leaves no loops or voices running.

## Practical continuation contract

1. Re-read current repository instructions and source before implementation. The baseline above identifies this publication, not a permanent execution HEAD.
2. Retain the full design horizon separately from the current demonstrator. Name what the demonstrator preserves, approximates, defers, or cannot prove.
3. Map tokens and controls to actual consumers with explicit units, ownership, accessible alternatives, and observable effect.
4. Complete the relevant interaction/error/cancellation states before promoting a reusable component.
5. Pair source/runtime checks with human correspondence review against the actual visual inspiration.
6. Keep proposed repairs unexecuted until a later implementation records its own revision, checks, and evidence.
